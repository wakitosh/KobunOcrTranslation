# Kobun OCR / Translation

古典籍画像のレイアウト認識、OCR翻刻、翻刻の人手修正、確認・公開、実験的な現代語訳をOmeka Sへ追加するモジュールです。NDL古典籍OCR-Liteをサーバ側で実行し、行枠の編集と読み順変更には、みんなで翻刻OCRをもとにしたUIを使用します。

公開画面では、Miradorに表示中のcanvasを対象に「このページを翻刻する」を実行できます。公開済みの確認データを優先し、存在しない場合は機械翻刻を作成して、両者の状態を明示します。翻刻と現代語訳は、画像を操作しながら比較できるタブ付きのモードレスポップアップに表示されます。ポップアップは上部をドラッグして移動でき、左右の下隅のハンドルで縦横にサイズを変更できます（ハンドルにフォーカスして矢印キーでも調整可能）。位置とサイズはスマートフォンの縦・横、タブレットの縦向き、大きい画面でそれぞれブラウザのlocalStorageに保存し、別の資料や再読込後にも復元します。

スマートフォンでは画面幅を使い、タブレットでは画像と比較できる幅で表示します。長い縦書き本文はウィンドウの高さに合わせて折り返し、狭いウィンドウの権利情報は1列に並べます。タッチ操作の範囲を広げ、ノッチやソフトキーボードで画面が狭くなった場合は表示範囲内へ補正します。キーボード表示中の一時的な縮小で、保存したサイズは置き換えません。

## 主な機能

- NDL古典籍OCR-Liteによるレイアウト認識と文字認識
- 縦書き・横書きの表示、左読み・右読み、キーボードとマウスによる行順変更
- `dcterms:identifier` とClean Urlを使う資料選択
- 権限を付与した役割による保存済み翻刻の修正
- 翻刻済みテキストの貼付、テキストファイルおよびWord（DOCX）からのページ単位取込
- 役割ごとの「自分が所有する資料」「閲覧できる全資料」の範囲指定
- 下書き、確認済み、公開の状態管理と版履歴
- 翻刻責任者の版記録と、公開済み翻刻への責任・権利表示
- 作成者・研究者識別子・役割・掲載誌・ISSN等・DOI・利用条件・推奨引用を含む研究成果情報
- 公開閲覧用キャッシュと編集用作業の分離
- ローカルLLMによる実験的な現代語訳と、管理者による訳文の直接入力・修正
- 訪問者自身のAPIキーによるOpenAI・Anthropic・Googleの現代語訳と、ブラウザ内の設定・キー管理
- Miradorの `#canvas=…` ディープリンクとの追従
- Omeka S 4のリソースページブロック「古典籍 OCR 閲覧支援」

機械生成の現代語訳は、図書館が確認した本文・訳とは限りません。公開画面ではこの状態を表示します。

ローカルLLMの標準プロンプトは、古語の語義、否定・願望・推量、踊り字の扱いと短い訳例を含み、原文の再掲や語句ごとの説明を避けて訳文を返すよう指定しています。指示に従わない出力や誤訳は残り、意味の正しさを保証するものではありません。OCRで欠字・誤認識が多い本文は、管理画面で翻刻を画像と照合・修正してから訳を作成してください。

バックエンド更新後は、処理完了を確認し、モジュール設定の「実行サービス」でworkerを再起動すると新版の標準プロンプトが適用されます。旧標準プロンプト（版2）は起動時に版6へ切り替わります。編集・確認・公開用の訳と版履歴は保持し、管理画面の再生成時から新しい版を記録します。RHELの実行用コピーの更新手順は[INSTALL_RHEL9.md](INSTALL_RHEL9.md)を参照してください。

## 必要環境

- Omeka S 4.x
- PHPのDOM・ZIP拡張（Word取込を使う場合）
- IIIF MediaとMiradorを表示できる構成
- Python 3.11環境のOCR workerと、常駐する運用サービス
- NDL古典籍OCR-LiteのONNXモデル
- 現代語訳を使う場合はllama.cppと、設定画面で選択したGGUFモデル

モデル、作業データ、ログ、認証トークンはモジュールディレクトリへ置かず、Web非公開の実行領域へ配置してください。RHEL 9.7の設置例では `/var/lib/kobun-ocr-translation` を使用します。

## インストール

RHEL 9.7では[INSTALL_RHEL9.md](INSTALL_RHEL9.md)のGitHub取得＋一括インストーラを推奨します。設置例はOmekaが`/opt/omeka-s`、バックエンドが`/opt/kobun-ocr-translation`です。Omekaの実際の配置先・PHP実行ユーザ・IIIFホストは設置環境に合わせて指定してください。設定・トークンの接続情報はWeb非公開領域から自動読込し、既存のOmeka設定は自動編集しません。

以下はZIP・手動設置の概要です。

1. ディレクトリ名を `KobunOcrTranslation` としてOmeka Sの `modules/` に配置し、管理画面で有効化します。
2. [DISTRIBUTION.md](DISTRIBUTION.md) のRHEL 9.7手順に従い、Python環境、OCR・LLMモデル、llama.cppをWeb非公開の実行領域へ準備します。
3. `config/local.config.php` でworker・運用サービスの接続先、PHPから読めるトークンファイル、許可するIIIFホストを設定します。
4. **運用サービスだけ**をsystemdで登録し、`sudo systemctl enable --now kobun-ocr-control.service`で起動します。workerとLLMサーバ用の常駐ユニットは不要です。
5. モジュール設定で現代語訳モデルと、翻刻を修正できる役割・資料範囲を選びます。全体管理者が同じ設定画面の「実行サービス」からworkerと、必要に応じてLLMサーバを起動します。

設定例：

```php
'kobun_ocr' => [
    'backend_url' => 'http://127.0.0.1:8766',
    'control_url' => 'http://127.0.0.1:8767',
    'token_file' => '/etc/omeka-s/kobun-backend-token',
    'image_hosts' => ['iiif.example.ac.jp'],
    'resource_hosts' => ['archive.example.ac.jp'],
    'public_ocr_pages_per_hour' => 24,
    'public_translations_per_hour' => 6,
],
```

モデルの初回取得はサーバ管理者が行います。設定画面の「未取得モデルの導入方法」に取得コマンドを表示します。候補と固定リビジョンは `worker/models.json` に記録しています。

取得済みモデルの切替は、モジュール設定の「実行サービス」で完結します。**LLMサーバを停止 →「起動するモデル」で選択 → LLMサーバを起動**の順に操作してください。設定フォームの保存は不要です。workerが稼働中の場合は新規処理受付を一時停止し、workerの停止・設定更新・復帰を自動で行います。停止中のworkerは自動起動しません。起動時にSHA-256を検証し、切替・起動操作の失敗時は元の設定へ戻します。未取得・容量不一致のモデルは選択できません。CPU／Metal、スレッド数、文脈長は維持します。

ローカルLLMの候補はQwen3-4B、Qwen3.5-9B、Qwen3.5-35B-A3B（いずれもQ4_K_M）です。35B-A3Bのモデルファイルは22.29GBで、十分なメモリが必要です。CPU実行に加え、macOSではMetalによるGPU実行を明示選択できます。切替手順は[LOCAL_MACOS.md](LOCAL_MACOS.md)、配布・容量の詳細は[DISTRIBUTION.md](DISTRIBUTION.md)を参照してください。

モジュール設定の「実行サービス」にはworkerとLLMサーバの稼働・準備状態、モデル名とCPU／Metal、workerの処理中件数を表示します。モデル読込中は状態を自動更新します。全体管理者だけが起動・停止・再起動・モデル切替できます。処理中ジョブがある間は停止・再起動・モデル切替を拒否します。workerに独立した自動起動サービスはありません。運用サービス自体が停止した場合は、RHEL 9.7では`sudo systemctl start kobun-ocr-control.service`で起動します。macOSのローカル環境では[LOCAL_MACOS.md](LOCAL_MACOS.md)を参照してください。既存の運用サービスは更新・再起動が必要です。

## 公開閲覧支援の設定

1. 「テーマ」→「リソースページを設定」で、アイテムの任意の領域へ「古典籍 OCR 閲覧支援」を割り当てます。
2. 公開画面でMiradorのページを開き、「このページを翻刻する」を実行します。

閲覧支援はブロックを割り当てたサイトだけで利用できます。

公開画面の現代語訳はサイト設定で個別に有効化します。公開済みデータは「図書館確認済み」、オンデマンド結果は「機械生成・未確認」と表示します。公開閲覧用の結果は、管理画面の編集・審査対象へ混在しません。

図書館が確認・公開した現代語訳があるページでは、その訳を表示し、訪問者の設定フォームと翻訳生成ボタンは表示しません。登録済みの設定・APIキーがある場合は、共用端末でも片付けられるよう消去ボタンだけを残します。翻刻だけが確認済みで訳がないページでは、許可された商用APIによる自分用の訳を作成できます。

### 閲覧支援の一時保存

図書館の編集・確認・公開用データは期限を設けず保存します。訪問者の機械生成結果は、資料を読むための一時的な支援情報として分離します。Omekaのメタデータ・検索・IIIFマニフェストへ自動登録しません。

| データ | 初期設定 |
|---|---|
| 訪問者の機械翻刻 | 生成から24時間の共有キャッシュ。実行要求があった場合に再利用 |
| 訪問者のローカルLLMの機械現代語訳 | この閲覧画面だけ。他の訪問者・タブへ共有しない |
| 私用のOCR・翻訳処理データ | 処理完了から60分後にサーバから削除 |
| 一時保存領域 | 1000件・1024 MiBを上限に、処理済みの古い結果から削除 |

全体管理者はモジュール設定の **「閲覧支援の一時保存」** で、翻刻・現代語訳それぞれの共有方法、有効期限、私用の保存時間、件数・容量上限を変更できます。使用状況も同じ画面で確認できます。共有する現代語訳の期限は、元の翻刻の期限を超えません。翻刻を共有しない場合は訳も共有しません。閲覧で有効期限は延長しません。

workerが毎分、期限切れの本文・画像コピー・機械生成の履歴・処理ログを削除します。処理中は削除せず、完了後に期限・上限を再確認するため、実行中の容量は一時的に上限を超える場合があります。OCRの重みや現代語訳のモデル・プロンプトが変わった場合は旧結果を再利用しません。商用APIの自分用の訳は従来どおりブラウザ内だけに保持します。

私用の訳は再読込・ページ移動で引き継がず、本文をlocalStorageやsessionStorageへ保存しません。「自分用の訳を作り直す」「自分用の訳を消去」で操作できます。ページ移動時にはサーバの私用データも消去要求を送ります。通信が途切れた場合も保存時間が過ぎると削除します。**ポップアップを閉じるだけの場合は、同じ画面で再表示できます。**

**0.11.0への更新時：** Omekaモジュールとworkerを両方更新し、処理完了後にworkerを再起動してください。期限や生成条件を持たない旧訪問者キャッシュは削除します。編集・確認・公開用データとその履歴は保持します。

### 機械生成キャッシュの削除・再生成

期限付き共有を選んだ結果は、全体管理者でログインし、公開ページの **「管理者用：機械生成キャッシュ」** から削除・再生成できます。現代語訳の操作は、現代語訳も「期限付き共有」にした場合だけ表示します。初期設定の自分用の訳は訪問者自身が消去・作り直します。管理画面の編集・確認・公開用データとは別の操作で、図書館確認済みデータには表示しません。

- 翻刻の再生成は、保存した画像から行の検出・文字認識をやり直します。成功時に以前の翻刻を置き換え、その翻刻に基づく機械現代語訳を削除します。翻刻の削除も、機械訳を同時に削除します。
- 機械現代語訳だけを削除・再生成する場合、翻刻を保持します。再生成には現在設定している図書館のローカルLLMを使用します。訪問者の商用API設定・APIキーは使用しません。
- 再生成中と失敗時は有効期限内の以前の結果を保持します。処理中の変更、古い版からの変更は拒否します。管理者の操作日時・操作者は一時結果の期限内だけ記録し、過去の本文の複製は残しません。削除した訳は処理ログからも除去します。

キャッシュは同じ画像を利用する訪問者・サイト間で共有するため、サイト管理者や翻刻編集者にはこの操作権限を与えていません。管理者の再生成は訪問者の時間当たり回数制限には含めませんが、実行部の処理待ち上限・保守状態・モデルの準備状態を確認します。公開現代語訳が無効のサイトでは、訳の操作も表示しません。訪問者が商用APIで作った「自分用の訳」はブラウザ内の結果であり、この共有キャッシュとは別です。

### 管理者による訪問者設定の制御

「モジュール」→「Kobun OCR / Translation」→「設定」の **訪問者の現代語訳設定** で、公開画面の設定フォームと各機能を制御します。全サイトに共通の設定です。各サイトで現代語訳全体を無効にする設定は引き続き使用できます。管理者の編集画面のLLM設定には適用しません。

- 設定フォーム全体の表示・非表示
- 利用できるLLM（ローカル、OpenAI、Anthropic、Google）を個別に許可
- 利用できる保存方法（このページだけ、ブラウザへの平文保存、暗号化保存）を個別に許可
- 訪問者によるLLM選択、モデルID変更、保存方法選択、APIキー入力・変更、接続確認を個別に許可
- LLM・保存方法の初期値、および商用LLMごとのモデルID初期値を指定

選択・変更を禁止した項目は管理者の指定値に固定します。モデル変更を禁止する場合は、訪問者が利用できる各商用LLMのモデルIDが必須です。フォームを非表示にする場合も、LLM・保存方法・モデルを管理者の指定値に固定します。LLMをローカルに固定する場合は商用モデルIDは不要です。APIキーは管理者設定へ保存しません。キー入力を禁止した場合は、許可範囲内の登録済みキーだけを利用できます。

| 運用例 | 設定 |
|---|---|
| ローカルLLMのみ | 「利用できるLLM」はローカルだけを許可。フォームを非表示にしてもローカルで生成可能 |
| 商用APIを許可し、保存は「このブラウザに保存」だけ | 必要な商用LLMを許可。「利用できる保存方法」は平文のブラウザ保存だけとし、保存方法の初期値も同じにする |
| モデルを統一 | モデルID変更を禁止し、許可する各商用LLMのモデルIDを入力 |
| 共用端末で保存を残さない | 保存方法は「このページだけ」だけを許可し、初期値も同じにする |

初期値は許可した選択肢から選び、LLMと保存方法はそれぞれ少なくとも1つ許可してください。矛盾する設定は保存できません。以前保存したLLM・保存方法が許可範囲外の場合、そのキーを自動転用せず、許可された方法での再登録を求めます。既存の保存情報は勝手に削除しません。消去操作は常に可能で、フォーム非表示時にも保存設定があれば消去ボタンを残します。暗号化キーのロック解除はフォーム表示中に使用できます。非表示のままでは、未登録・未解除の商用キーは利用できません。

変更は訪問者が公開ページを再読込した後に反映されます。ローカルLLMの公開実行はサーバ側でも制限します。商用APIの許可は、このモジュールの画面と呼出処理に適用します。

### 訪問者の商用LLM設定

モードレスウィンドウの「現代語訳」タブで「現代語訳の設定」を開きます。管理者が変更していなければ初期値は図書館のローカルLLMです。商用APIを使う場合は許可されたOpenAI（GPT）、Anthropic（Claude）、Google（Gemini）から選び、自分のAPIキーを登録します。接続確認が許可されていれば「接続確認・モデル一覧を取得」で利用可能なモデル候補を取得し、モデルIDを選択または入力して設定を再登録してください。モデルIDが分かっていれば、キーとモデルを一度に登録できます。接続確認はモデル一覧の取得だけで、訳文生成や資料本文の送信は行いません。

設定とキーの保存方法は次の3通りです。

| 保存方法 | 動作 |
|---|---|
| このページだけ（初期値・共用端末向け） | メモリだけで保持し、localStorage・sessionStorageへ保存しない。再読込・ページ移動でキーを消去 |
| このブラウザに保存 | 同じオリジンのlocalStorageに設定とAPIキーを平文で保存。個人端末向け |
| パスフレーズで暗号化して保存 | localStorageに設定と暗号化したキーを保存。ページを開くたびに解除が必要。パスフレーズは保存しない |

暗号化保存はPBKDF2（SHA-256、310,000回、ランダムsalt）で鍵を導出し、AES-GCM（256 bit、ランダムIV）を使います。提供者・モデルIDも認証対象として結び付け、保存情報を別サービスへ変更してもキーを解除できないようにしています。暗号化用パスフレーズは12文字以上で、設定・モデルを変更して保存するときも入力します。暗号化は保存中のキーを保護しますが、利用中の不正なスクリプトや端末操作からは保護できません。

15分操作がない場合、利用中のキーと入力欄を消去します。保存済み設定は残ります。「ロックする」は暗号化保存の解除状態を終了し、「保存設定・キーを消去」はブラウザの保存内容も消去します。他のタブから設定が削除・変更された場合にも追従します。共用端末では「このページだけ」を選び、利用後に消去操作を行ってください。

商用APIへ送るのは翻訳指示と翻刻本文です。画像、翻刻責任者、研究成果・権利情報は送信しません。キーは各提供者の認証ヘッダーだけで使用し、Omekaやworkerには送信・保存しません。料金はAPIキーの契約者負担であり、外部送信と費用負担を毎回確認してから実行します。失敗時の自動再送は行いません。中止しても提供者側の処理・課金を取り消せるとは限りません。

公開画面の商用訳は、そのページを開いている間だけの自分用の結果です。提供者とモデル名を表示し、図書館の確認データや他の訪問者向けキャッシュには保存しません。「自分用の訳を消去」、設定の消去、画像ページの変更・ページ移動で破棄します。サイト設定で公開現代語訳を無効にした場合は、設定UIを含む現代語訳タブ全体を表示しません。

既定の利用上限は、ブラウザのセッションとサイトごとに新規OCR 24ページ／時、現代語訳6回／時です。レイアウト認識と文字認識をまとめて1ページと数え、保存済みの結果を開く操作は数えません。上限時は再試行までの時間と現地時刻を表示します。運用環境に合わせて上記の `kobun_ocr` 設定で変更できます。

## 管理画面の作業

管理画面の「古典籍 OCR・現代語訳」から次の順で操作します。

1. `dcterms:identifier` またはClean Urlで資料を開き、画像ページを選びます。
2. レイアウトを認識し、行枠、縦横、読み方向、読み順を調整します。
3. OCRを実行し、画像と照合して翻刻を修正・保存します。
4. 必要に応じて本文の範囲を確認し、LLMで現代語訳を作成するか、管理者が訳文を直接入力します。現代語訳を作らず次へ進むこともできます。
5. 「確認・公開」で翻刻責任者と研究成果・権利情報、確認メモを入力し、下書きから確認済み、公開へ変更します。確認済み以降は翻刻責任者が必須です。

管理画面の現代語訳ステップにも同じLLM設定があります。商用LLMはブラウザから呼び出し、生成後に訳を確認・修正して「生成した現代語訳を保存」を押します。保存時に本文・対象行・モデル名・提供者・プロンプト版・修正の有無・認証済みの取込者を版履歴へ記録し、公開状態を下書きへ戻します。この記録は管理者がブラウザから取り込んだという記録であり、提供者による生成証明ではありません。保存済みの版にはキー・パスフレーズを含めません。商用API利用時はローカルLLMサーバの起動は不要ですが、OCRと作業保存にworkerを使用します。

既存の翻刻がある場合は、レイアウト調整または翻刻確認画面の「翻刻済みテキストを取り込む」から貼り付けるか、`.txt`／`.docx`を選択できます。Wordでは `［一オ］` などの丁付をページ区切りとして検出し、右ルビ・上側注記を `^(...)`、左ルビ・下側注記を `_(...)`、下線を `＿...＿` の平文記法へ変換します。通常のWordルビに加え、旧式のEQフィールドで配置された左右のルビも解析します。原稿の表題、執筆者、掲載誌、号、発行主体、刊行年も入力候補として抽出します。候補ページは複数選択でき、選択した本文を文書内の順につないで、画像の行数と一致させてから反映します。

入力した翻刻責任者、作成者・所属・役割、掲載誌情報、DOI・掲載先、権利者・権利状態、利用条件、推奨引用は、公開中の翻刻とともに公開画面へ表示されます。責任・権利表示の変更も版履歴に記録されます。公開後に行枠、翻刻、翻訳用本文、訳文を変更すると下書きへ戻ります。過去の版、処理条件、編集者は履歴に保持されます。
